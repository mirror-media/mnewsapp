# 為什麼不先重構，AI agent 會每次都花更多 token

## 結論

會，而且通常不是一次性的成本，而是每一次任務都會重複發生。

當專案架構不一致、規則混用、生命週期分散時，AI agent 在真正開始修改功能之前，必須先花更多上下文成本去理解：

- 這個頁面目前是用 `Bloc`、`Cubit`、`GetX`，還是混用
- controller / bloc 是在哪裡建立、在哪裡銷毀
- 資料流是從 page、controller、bloc、service 還是 provider 進來
- 同類型頁面為什麼寫法不一致
- 哪些是正式架構，哪些只是歷史殘留

這些理解成本都會直接轉成 token 消耗。

## 為什麼是「每一次」都會多花

AI agent 不會像人一樣長期記住整個專案的細節。

即使同一個 agent 連續工作，只要任務換到另一個模組，或上下文重新整理，它仍然需要重新確認很多專案規則。  
如果專案本身規則不一致，agent 就無法只用一套固定假設做事，只能額外讀更多檔案來驗證。

所以常見情況會變成：

- 改搜尋頁，也要回頭確認 service 和舊 bloc 是否還在耦合
- 改列表頁，也要多追 category、provider、首頁 section 切換
- 修一個 bug，也要先確認是不是混合狀態管理造成的副作用

這些都會讓 token 消耗在「理解專案」而不是「完成需求」。

## 什麼情況會特別耗 token

以下幾種狀況最容易讓 AI agent 額外消耗上下文：

### 1. 狀態管理混用

同一個專案同時存在：

- `Bloc`
- `Cubit`
- `GetX`

agent 每次都要先判斷眼前模組屬於哪一套，再決定資料怎麼追。

### 2. 依賴注入方式不一致

如果同時出現：

- `Binding`
- `Get.put`
- `Get.lazyPut`
- `BlocProvider`
- widget 內 `init`

agent 就不能預期 controller 或 bloc 一定在哪裡建立，必須額外搜尋。

### 3. 頁面生命週期不一致

有些 controller 是全域，有些是 page-scoped，有些在首頁切 section 時手動建立與刪除。  
這會讓 agent 很難快速判斷修改某個頁面是否會影響其他地方。

### 4. 同類型模組寫法不同

例如都是列表頁，但：

- 有的走 bloc
- 有的走 getx
- 有的 service 直接回 model
- 有的中間還包 provider / fallback

這種不一致會讓「可複製模板」失效，agent 無法快速沿用既有模式。

## 實際會帶來什麼影響

### 對 AI 協作

- 每次任務要先讀更多檔案
- 每次修改前要花更多 token 建立上下文
- 容易把注意力浪費在辨識規則，而不是直接完成改動
- 越大的功能或越核心的頁面，額外成本越高

### 對工程團隊

- 同樣需求，AI 協作效率會下降
- 產出的修改更需要人工補充校正
- 每次交付前的驗證範圍容易變大
- 團隊會誤以為是 AI 不夠準，其實很多時候是專案規則本身不穩定

### 對 PM / 時程

- AI 協作並不會自動讓混亂專案變快
- 如果架構不一致，AI 也要先花時間「考古」
- 需求估時會更難穩定
- 同樣看起來小的任務，實際 token 與工作量可能被放大

## 為什麼先做重構會更省

重構的價值不只在於人類工程師更好維護，也在於讓 AI agent 有一套穩定規則可依循。

如果專案逐步收斂成：

`Page -> Controller -> Service -> API`

而且新功能都遵守同一套規範，那 agent 在後續任務裡通常可以：

- 用更少檔案建立上下文
- 更快找到真正修改點
- 用更穩定的方式產出改動
- 減少重複理解成本

換句話說，重構不是增加 AI 成本，而是降低後續每一次 AI 協作的平均成本。

## 建議怎麼對外說

可以用這句話概括：

> 如果專案不先收斂，AI agent 每次都要花更多 token 去理解混亂結構，而不是直接完成需求。

如果要更完整一點，可以這樣說：

> AI 可以加速開發，但前提是專案規則要夠一致。  
> 當架構混用、責任邊界模糊時，AI 每次都必須先花額外成本辨識專案規則，這些成本會在每一次任務中重複發生。

## 建議放進團隊共識

後續如果要把 AI 協作正式納入開發流程，建議把下面幾點一起列為共識：

- 新功能不要再新增新的狀態管理模式
- 頁面資料流固定走 `Page -> Controller -> Service`
- 頁面級依賴用 `Binding`
- 完成重構的模組要把舊寫法清掉，不要雙軌並存
- 把 AI 協作成本視為架構品質的一部分，而不是單純工具問題
